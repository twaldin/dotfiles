# UI guide

- Make the user's main task and next action clear. Use hierarchy, spacing, typography, and concrete copy to make related information easy to scan.
- Reuse the project's design tokens and components. Keep project branding with its project; add a new visual convention only when the design needs it.
- Use native semantic elements, accessible names, labeled controls, visible keyboard focus, and sensible focus order. Use established accessible components for complex interactions.
- Handle the states the feature can actually reach: loading, empty, success, validation errors, and failures. Preserve useful input when an action fails.
- Check relevant narrow and wide layouts, long content, keyboard interaction, and zoom. Respect reduced-motion preferences and ensure information is distinguishable without color alone.
- Show failures and results where the user can act on them. Make destructive actions and their consequences understandable within the project's interaction conventions.
- Validate the actual rendered feature and its important interaction path using available tools. Automated checks, visual inspection, and assistive-technology testing provide different evidence; report only what was checked.

For detailed accessibility criteria or unfamiliar platform behavior, consult the relevant current primary documentation. A routine UI check is not a claim of full accessibility conformance.
